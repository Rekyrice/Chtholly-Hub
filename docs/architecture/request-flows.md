# 核心请求链路

## 阅读时机

排查跨控制器、服务、缓存、事件和外部依赖的问题，或修改会影响多个领域的行为时阅读本章。每条链路只描述当前源码已实现的路径。

## 读完能回答的问题

- 十条高价值链路从哪个入口触发，在哪里提交同步结果？
- 哪些工作异步执行或经过缓存，状态最终落在哪里？
- 依赖失败时返回错误、保留主事务，还是返回降级结果？
- 哪些测试最接近该链路？

## 1. 登录、刷新与鉴权

- **触发入口**：[AuthController](../../apps/server/src/main/java/com/chtholly/auth/api/AuthController.java) 的 `/api/v1/auth/login`、`/token/refresh`；受保护请求进入 [SecurityConfig](../../apps/server/src/main/java/com/chtholly/auth/config/SecurityConfig.java) 配置的 Resource Server。
- **同步主链**：[AuthService](../../apps/server/src/main/java/com/chtholly/auth/service/AuthService.java) 只把注册、登录、刷新/登出与密码恢复分派给独立用例服务。注册由 [AuthRegistrationService](../../apps/server/src/main/java/com/chtholly/auth/service/AuthRegistrationService.java) 的外层 MySQL 事务约束用户创建、首枚 refresh membership 尝试与提交顺序，但 Redis 不参与 MySQL 原子提交；新用户尚未提交，只有窄接口 [PendingUserRefreshTokenStore](../../apps/server/src/main/java/com/chtholly/auth/token/PendingUserRefreshTokenStore.java) 可以在当前事务看见 `epoch=1`、而独立已提交快照还看不见该用户时写入 `mysql:1`，回滚窗口由补偿处理。登录先检查失败锁并定位 userId，再捕获 MySQL refresh epoch、按 id 重读最新用户凭据，然后验证密码/验证码和封禁；签发 refresh token 时以捕获的 epoch 执行条件写并在写后重读 MySQL，密码重置或用户级撤销只要在校验期间推进过 epoch，本次登录就会失败并删除本轮 membership。不存在账号、错误密码和错误验证码统一返回 `INVALID_CREDENTIALS`，封禁仍保留 `USER_BANNED`。刷新先验证 JWT 类型、用户和封禁状态，再由 [RefreshTokenStore](../../apps/server/src/main/java/com/chtholly/auth/token/RefreshTokenStore.java) 原子消费旧 jti、写入新 jti，并以写前/写后 MySQL epoch 隔离并发撤销。Bearer access token 经 Spring Security 解码，随后 [BannedUserFilter](../../apps/server/src/main/java/com/chtholly/admin/security/BannedUserFilter.java) 再检查用户封禁。
- **异步/缓存**：验证码、发送配额、失败窗口和 refresh token 状态位于 Redis，无消息队列。验证码发送间隔与每日额度使用相同 Cluster slot 内的一段 Lua 原子检查并预留，验证码和额度新 key 都只保存场景与目标标识的 SHA-256 摘要，不暴露邮箱或手机号；验证码 Hash 的完整写入与 TTL、一次性消费、失败次数封顶分别由单 key Lua 完成。迁移期会只读仍在 TTL 内的旧验证码 key，并把旧 interval/daily 状态纳入首次新额度预留；新请求不再写旧 namespace。登录成功、凭据失败、锁定和封禁都会 best-effort 写登录日志；审计存储失败不会放宽凭据/封禁判断，也不会反向阻断已成功的登录。注册成功审计与 `UserRegisteredEvent` 只在 MySQL `afterCommit` 后分别 best-effort 执行，彼此失败不影响已经提交的用户。
- **状态**：用户、密码摘要和 `refresh_session_epoch` 在 MySQL；refresh token 只使用 Redis Cluster slot 内的 `auth:rt:{userId}:{jti}`，value 为 `mysql:<epoch>`。用户级撤销推进 MySQL epoch；单 token 撤销删除新旧 key 并写有限期 fence，防止在途旧请求复活 membership。V29 后旧裸 value/key 均不迁移，既有 refresh session 一次性失效，access token 本身仍无服务端 session。
- **失败/降级**：凭据、token、封禁、MySQL epoch 或 Redis membership 任一不可判定时拒绝请求；没有把 refresh token 状态降级为纯 JWT 校验。注册阶段的 JWT 或 Redis 签发失败会回滚用户；事务回滚或完成状态未知时，`afterCompletion` 会 best-effort 删除本轮 pending membership，删除前重新确认不存在已提交用户，避免在提交结果不确定时误删真实会话。注册验证码是一经成功验证就消费的 Redis 一次性事实，后续用户或 token 写入失败不会恢复验证码。密码恢复以单条 MySQL SQL 同时写新密码并推进 epoch，Owner 首次补密码也走相同用例，不依赖 Redis 撤销成功；旧密码并发登录不能进入新 epoch。V29 必须在停止全部旧节点后迁移并一次性切换，不支持滚动混部。开发/测试 profile 用本地文件交付验证码且应用日志不含验证码；其他 profile 装配明确失败的 sender，代码发送接口返回配置错误而不会把凭据写入服务器文件。验证码保存或投递失败会按随机写入版本删除不可交付值，不会让较早的失败请求误删后来成功发送的新码，并用带 nonce 的 Lua 补偿本次间隔/每日额度；新验证码的 legacy fence 阻止同目标旧明文值在新值消费后重新生效，清理或补偿异常作为 suppressed cause 保留而不覆盖原始失败。

## 2. 文章发布与缓存失效

- **触发入口**：[PostController](../../apps/server/src/main/java/com/chtholly/post/api/PostController.java) 的 `/api/v1/posts/{id}/publish` → [PostServiceImpl](../../apps/server/src/main/java/com/chtholly/post/service/impl/PostServiceImpl.java)。
- **同步主链**：正文上传先写入随机不可变对象键；[PostServiceImpl.confirmContent](../../apps/server/src/main/java/com/chtholly/post/service/impl/PostServiceImpl.java) 本身不声明事务，[PostDraftCommandService.prepareContentBinding](../../apps/server/src/main/java/com/chtholly/post/service/impl/PostDraftCommandService.java) 使用 `NOT_SUPPORTED`，即使未来上层携带事务也会先挂起，在无事务阶段校验草稿快照、键归属、size、SHA-256、对象字节事实与 URL；`bindPreparedContent` 使用 `REQUIRES_NEW`，只在独立短事务内用 `SELECT ... FOR UPDATE` 复核草稿和所有者并原子绑定正文元数据与 `PostContentConfirmed` Outbox。发布随后锁定草稿，以状态 CAS 发布、补齐唯一 slug、同步标签，并在同一事务写 `PostPublished` Outbox。元数据、可见性和删除也复用聚合行锁，避免按陈旧状态更新标签计数。
- **异步/缓存**：事务提交后的低延迟路径、Kafka 消费者与定时恢复任务都只进入 [PostOutboxProjectionProcessor](../../apps/server/src/main/java/com/chtholly/post/outbox/PostOutboxProjectionProcessor.java)，再按 MySQL 当前状态幂等修复详情/Feed 缓存、搜索、RAG、作者计数与关注 timeline。处理器以 `REQUIRES_NEW` 事务锁定 `post_projection_cursor`：已有回执的重复事件直接跳过；事件 ID 不大于游标但 Outbox 父行仍存在且回执缺失时，仍重跑全部幂等投影并补回执，但不回退游标；父 Outbox 与级联回执已按保留期清理时，把该旧消息视为清理后的延迟重复并直接跳过；只有较新的事件在投影与回执都成功后才推进游标。较新事件若缺少父 Outbox，不能走迟到重复快路径：幂等投影后写回执会因父行约束失败，MySQL 事务回滚、游标保持不变并向调用方抛错；Kafka 消费者按既有重试/DLQ 策略处理，不能静默 ACK。完整 Kafka/Canal 使用 [PostOutboxProjectionConsumer](../../apps/server/src/main/java/com/chtholly/post/outbox/PostOutboxProjectionConsumer.java) 作为低延迟主路径；[PostProjectionRecoveryJob](../../apps/server/src/main/java/com/chtholly/post/outbox/PostProjectionRecoveryJob.java) 始终以仍存在且无回执的 MySQL Outbox 为恢复事实。
- **状态**：文章、标签和 Outbox 在 MySQL；正文对象已在发布前确认；Feed/详情/RAG/ES/timeline 都是派生状态；`post_projection_cursor` 是每帖顺序栅栏和跨清理周期保留的事件高水位。`post_projection_receipt` 只表示对应仍在保留窗口中的 Outbox 投影已经成功完成，不会因游标更高而自动成立，并随父 Outbox 级联清理。
- **失败/降级**：草稿不存在、所有者不符、对象摘要不一致或状态竞态时失败；对象 I/O 不持有 MySQL 行锁。提交后的任一严格投影失败不会撤销文章，也不会写回执或推进游标。回放按固定高水位继续处理后续事件，并在下一轮重新发现失败行。RAG 正文读取复用受控超时的 `searchContentRestTemplate`，切片使用由帖子、源指纹和位置组成的确定性文档 ID；每帖跨节点 mutation 由 Redisson watchdog 锁串行，只有 completion manifest 404/缺失被视为幂等，旧 chunks 删除 timeout/failure/version conflict、向量写入、refresh shard 部分失败或 manifest 写入异常都会向回放层冒泡。检索还会回查 MySQL 可见性和当前摘要，不能把残留派生文档当作授权事实。
- **代表性测试**：[PostServiceImplTest](../../apps/server/src/test/java/com/chtholly/post/service/impl/PostServiceImplTest.java)、[PostMapperStateTransitionContractTest](../../apps/server/src/test/java/com/chtholly/post/mapper/PostMapperStateTransitionContractTest.java)、[PostProjectionRecoveryJobTest](../../apps/server/src/test/java/com/chtholly/post/outbox/PostProjectionRecoveryJobTest.java)、[PostOutboxProjectionProcessorTest](../../apps/server/src/test/java/com/chtholly/post/outbox/PostOutboxProjectionProcessorTest.java)、[PostProjectionCursorMapperIT](../../apps/server/src/test/java/com/chtholly/integration/PostProjectionCursorMapperIT.java)、[RagIndexServiceTest](../../apps/server/src/test/java/com/chtholly/llm/rag/RagIndexServiceTest.java)、[PostPublishingGoldenPathIT](../../apps/server/src/test/java/com/chtholly/integration/PostPublishingGoldenPathIT.java)。

## 3. Feed 与个性化推荐

- **触发入口**：公开/关注 Feed 从 [PostController](../../apps/server/src/main/java/com/chtholly/post/api/PostController.java) 的 `/feed`、`/feed/following` 进入 [PostFeedServiceImpl](../../apps/server/src/main/java/com/chtholly/post/service/impl/PostFeedServiceImpl.java)；个性推荐从 [RecommendationController](../../apps/server/src/main/java/com/chtholly/recommendation/api/RecommendationController.java) 进入 [RecommendationService](../../apps/server/src/main/java/com/chtholly/recommendation/RecommendationService.java)。
- **同步主链**：公开 Feed 读取分页/游标列表并批量补齐作者、计数和当前用户点赞收藏；评论总数由 [CommentServiceImpl](../../apps/server/src/main/java/com/chtholly/comment/service/impl/CommentServiceImpl.java) 按本次结果集一次聚合查询 MySQL，包含回复并排除软删除行，缓存命中后也会用当前事实覆盖旧值。关注 Feed 由 [FollowingPostFeedQueryService](../../apps/server/src/main/java/com/chtholly/post/service/impl/FollowingPostFeedQueryService.java) 编排：Redis timeline 与大 V 作者缓存只提供候选，每批候选都由 MySQL 重新校验文章已发布、可见性属于 `public/followers`，且当前仍存在 active following 关系。推荐先构建 [UserInterestProfile](../../apps/server/src/main/java/com/chtholly/recommendation/UserInterestProfile.java)，融合兴趣标签、内容相似和可选协同过滤候选。
- **异步/缓存**：公开 Feed 使用 Caffeine L1、Redis L2、SingleFlight 与热 key 检测；发布/关注事件维护 Redis timeline 与画像。关注 Feed 每批扫描 50 条、最多检查 1000 个候选，并在扫描结束后 best-effort 批量清理失效 timeline 项，避免边扫描边删除造成 Redis rank 漂移。作者达到大 V 阈值时进入拉模式；粉丝数降回阈值以下后，下一次文章投影会先把保留期内、对粉丝可见的文章幂等回填到当前粉丝 timeline，全部成功后才移除大 V 标记，避免切回推模式时历史文章消失。
- **状态**：文章、发布状态、可见性和 active following 关系在 MySQL；列表片段、用户交互、timeline、作者候选和画像在 Redis/进程缓存，均不能越过 MySQL 授权；推荐候选依赖 ES 与内容分析读模型。文章详情即使命中共享缓存也先读取 MySQL audience 快照，只有当前仍为 `public/published` 且缓存同样是 public 时才复用；`followers` 文章只对所有者或当前 active follower 开放。
- **失败/降级**：无用户或画像无信号时推荐热门；内容理解异常被跳过。ES 推荐查询失败会限制候选能力；公开 Feed 缓存未命中回源 MySQL。关注 Feed 在 Redis timeline/大 V 候选读取失败、深分页、扫描达到上限或候选不足以覆盖请求页时，直接用 MySQL active-following 查询按 `publish_time DESC, id DESC` 稳定分页；MySQL 失败向上抛出，不返回未授权或伪完整结果。
- **代表性测试**：[PostFeedServiceImplEnrichTest](../../apps/server/src/test/java/com/chtholly/post/service/impl/PostFeedServiceImplEnrichTest.java)、[PersonalPostFeedServiceTest](../../apps/server/src/test/java/com/chtholly/post/service/impl/PersonalPostFeedServiceTest.java)、[PostDetailQueryServiceTest](../../apps/server/src/test/java/com/chtholly/post/service/impl/PostDetailQueryServiceTest.java)、[FeedTimelineServiceTest](../../apps/server/src/test/java/com/chtholly/post/feed/FeedTimelineServiceTest.java)、[RecommendationServiceTest](../../apps/server/src/test/java/com/chtholly/recommendation/RecommendationServiceTest.java)。

## 4. 点赞/收藏事实与异步读投影

- **触发入口**：[ActionController](../../apps/server/src/main/java/com/chtholly/counter/api/ActionController.java) 的 `/like`、`/unlike`、`/fav`、`/unfav` → [CounterServiceImpl](../../apps/server/src/main/java/com/chtholly/counter/service/impl/CounterServiceImpl.java) → [CounterReactionCommandService](../../apps/server/src/main/java/com/chtholly/counter/service/CounterReactionCommandService.java)。
- **同步主链**：命令校验实体与用户，在同一 MySQL 事务锁定实体 reaction snapshot epoch，并把 `counter_reaction` 设置为目标状态。只有关系真实变化时才写一条 `CounterReactionChanged` Outbox；任一写入失败会让关系、快照准备与 Outbox 一起回滚。写接口直接返回事务已确定的目标状态，不回读异步 Bitmap。
- **异步/缓存**：只有 `KAFKA_ENABLED=true` 且 `CANAL_ENABLED=true` 时，Canal-compatible Outbox 消息才经 `canal-outbox` 进入 [CounterReactionOutboxConsumer](../../apps/server/src/main/java/com/chtholly/counter/event/CounterReactionOutboxConsumer.java)；任一开关关闭时，[CounterReactionLocalAdapter](../../apps/server/src/main/java/com/chtholly/counter/event/CounterReactionLocalAdapter.java) 在 `AFTER_COMMIT` 调用相同核心，[CounterReactionLocalOutboxReplay](../../apps/server/src/main/java/com/chtholly/counter/event/CounterReactionLocalOutboxReplay.java) 再从 MySQL 恢复未完成行。两个开关只负责选路，不探测 CDC 健康；选择 Kafka 路径前必须确认 CDC 可达，运行时没有自动本地回退。[CounterReactionEventProcessor](../../apps/server/src/main/java/com/chtholly/counter/event/CounterReactionEventProcessor.java) 以 `REQUIRES_NEW` 开启事务，[CounterAggregationProcessor](../../apps/server/src/main/java/com/chtholly/counter/event/CounterAggregationProcessor.java) 以 `REQUIRED` 加入并锁定 snapshot、登记 Inbox、计算同 epoch 快照；随后处理器分块批量回查 MySQL 当前终态，用 Lua 幂等维护 Bitmap/SDS，再提交事务。事件携带实际变化、epoch 与定位信息，不覆盖 MySQL 终态。
- **状态与读取**：`counter_reaction` 是成员关系唯一事实；Bitmap 是高频成员读投影，SDS 与 `counter_snapshot` 是计数投影，`counter_event_inbox` 保存事件幂等与事件级副作用发布回执。实体完整性标记只在一次全量重建完成后发布；标记有效且结构合法时，单条和 Feed 批量状态读取使用 Bitmap；标记缺失、版本错误或结构不完整时，按实体/指标分组并以最多 500 个关系键一批回退 MySQL，避免 N+1。Redis 网络、管道或 Lua 异常直接失败；读请求不会触发校准。
- **失败/恢复**：关系提交不依赖 Redis 或 broker 成功；Kafka 路径用 5/30/120 秒的持久 retry envelope，并在 broker 确认转发后才 ACK；未到期 retry 通过 `nack` 保留原记录，可能形成分区头阻塞。普通自动重试记录使用 `RETRYING`。第三次失败转入 DLQ 并记录 `DEAD` 后，完整 Kafka 模式没有并行的 MySQL Outbox 扫描，修复根因后须由管理员显式重放。`POST /api/v1/admin/dead-letters/{id}/replay` 以唯一 attempt token CAS 抢占 `DEAD → REPLAYING`，由 MySQL 时钟写入 `replay_started_at` 和 `replay_deadline_at`；截止时间按 producer 实际 `max.block.ms + delivery.timeout.ms + 30 秒` 计算。同步发送抛错会尽力用同 token 恢复 `DEAD`；非空 broker `SendResult` 的终态回调用同 token 改为 `PENDING`，异步失败或空结果改为 `UNCERTAIN`。HTTP 请求只等待 10 秒：等待超时或线程中断时 producer future 继续执行，行保持 `REPLAYING`，回调稍后仍可收敛；回调的 MySQL 更新失败也保留 `REPLAYING`。列表和单次操作响应中的 `replayAttemptToken` 是当前代际的并发标识，不是授权凭证。在原应用实例和请求已确认不会恢复执行后，只有超过数据库截止时间且 token 匹配的行才能通过 `POST .../{id}/recover-expired?attemptToken={replayAttemptToken}` 转为 `UNCERTAIN`；该接口不发送消息，也不直接开放再次重放。管理员核对 broker/consumer 证据后，再用 `POST .../{id}/resolve?attemptToken={replayAttemptToken}&published=true|false` 把同一代 `UNCERTAIN` 变为 `PENDING` 或 `DEAD`。attempt token 对 broker 回调、过期恢复和人工 resolve 全部做 CAS，旧回调与延迟人工请求都不能完成新的 claim；`REPLAYING` 和普通 `RETRYING` 均不能直接 resolve。本地回放每 5 秒以固定高水位和 keyset 分页扫描缺少 Inbox 或 `side_effects_published_at` 为空且至少已提交 5 秒的 Outbox，单页失败后继续推进当前有限扫描，并在下一轮重试失败行。健康页使用一个事务批次；Lua 完成流水线后会返回无法投影的精确关系键，处理器以 relation key 为隔离单位，同一键的全部事件一起留待恢复，并将其余健康 peer 合成一个批次重试一次。未携带失败键的异常整批立即失败，不做递归二分或逐事件 SQL/Redis。投影处理失败回滚本次 Inbox/快照事务，但不回滚关系/Outbox；第一次流水线已写入的健康 Redis 终态允许存在，第二个健康批次会幂等确认投影并提交 Inbox/快照。Outbox 重放或 [CounterCalibrationService](../../apps/server/src/main/java/com/chtholly/counter/service/impl/CounterCalibrationService.java) 恢复失败键。校准在实体级 Redisson 锁与 token fence 下删除完整标记，直接有界清理并分页重写 live shard；Redis 先写 prepared 状态，MySQL 提交新 epoch/绝对计数后再发布完整标记。并发写会标脏 fence 并使校准重试，失败保持投影不完整；周期扫描使用固定 MySQL 字典序高水位，不被持续新增实体饿死。
- **副作用边界**：处理事务提交后，每个尚无发布回执的真实 Outbox 变化都发布 Spring 事件，包括旧 epoch 事件；旧 epoch 只是不改变当前快照。全部同步监听器调用返回后，[CounterReactionSideEffectReceiptService](../../apps/server/src/main/java/com/chtholly/counter/event/CounterReactionSideEffectReceiptService.java) 才写 `side_effects_published_at`。向发布器传播的监听器失败会让回执保持为空并由 Outbox 重放，但回执不是逐监听器的：已发生的非事务通知、缓存失效或画像更新可能在后续重放中重复；反过来，某个监听器若捕获内部失败并正常返回，事件级回执仍可能成功，缺失的那一项副作用不会被该回执机制自动发现。24 小时 Redis 标记只在回执提交后尽力写，不作为待处理事件的拦截条件。该链路不宣称 MySQL、Redis、Kafka 跨资源原子提交或 exactly-once。

## 5. 关注关系与 Outbox

- **触发入口**：[RelationController](../../apps/server/src/main/java/com/chtholly/relation/api/RelationController.java) 的 `/follow`、`/unfollow` → [RelationServiceImpl](../../apps/server/src/main/java/com/chtholly/relation/service/impl/RelationServiceImpl.java)。
- **同步主链**：[RelationServiceImpl](../../apps/server/src/main/java/com/chtholly/relation/service/impl/RelationServiceImpl.java) 是命令/查询兼容门面；关注命令先用纯参数校验拒绝自己关注，再执行 Redis 令牌桶，随后确认 source/target 用户存在，最后在同一 MySQL 事务写 `following` 与一行 Outbox；Outbox 影响行数不是 1 时整个命令失败。取关更新 `following` 并写 Outbox。重复关注复用原关系 ID，但刷新创建/更新时间以保持列表排序与权威写模型一致。
- **事务/异步边界**：关注通知使用 `BEFORE_COMMIT`，由 [NotificationEventListener](../../apps/server/src/main/java/com/chtholly/notification/listener/NotificationEventListener.java) 在关注事务内写入同一个 MySQL；通知失败会让关注事实和 Outbox 一起回滚。Feed timeline 与取关清理由严格 `AFTER_COMMIT` 监听器处理，回滚或非事务发布不会触发。Kafka/Canal 启用时 [CanalKafkaBridge](../../apps/server/src/main/java/com/chtholly/relation/outbox/CanalKafkaBridge.java) 转发 Outbox，[CanalOutboxConsumer](../../apps/server/src/main/java/com/chtholly/relation/outbox/CanalOutboxConsumer.java) 调用 [RelationEventProcessor](../../apps/server/src/main/java/com/chtholly/relation/processor/RelationEventProcessor.java) 幂等维护 `follower`、Redis ZSet 和用户计数；follower upsert 会同步权威 relation ID、状态与时间，可修复历史错误投影 ID。
- **状态**：`following` 是同步写模型，Outbox 与它同事务；`follower`、关系 ZSet 和关注/粉丝数是异步派生状态。
- **失败/降级**：限流返回未关注；重复写不产生新关系。Kafka/Canal 关闭时 Outbox 仍积存在 MySQL，本地事件只覆盖通知/timeline，不会执行 `RelationEventProcessor`，因此不能把它视为 fan 侧完整 fallback。

## 8. Agent WebSocket、上下文、工具与记忆

- **触发入口**：[AgentWsTicketController](../../apps/server/src/main/java/com/chtholly/agent/api/AgentWsTicketController.java) 签发票据，客户端连接 `/api/v1/agent/ws`。[AgentWebSocketHandler](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentWebSocketHandler.java) 只适配 Spring 回调；认证/连接补偿由 [AgentWebSocketConnectionLifecycle](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentWebSocketConnectionLifecycle.java) 完成，入站校验与任务派发由 [AgentWebSocketProtocolDispatcher](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentWebSocketProtocolDispatcher.java) 完成。`chat` 携带客户端 `requestId`；服务端先捕获 memory generation 快照，再取得轮次所有权、生成 `turnId` 并返回 `accepted`。会话清空与删除走 [AgentSessionMemoryController](../../apps/server/src/main/java/com/chtholly/agent/api/AgentSessionMemoryController.java) 的已认证幂等 `DELETE /api/v1/agent/sessions/{sessionId}/memory`；前端收到成功响应后才删除本地消息或会话。
- **同步主链**：[AgentWebSocketTurnAdmissionService](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentWebSocketTurnAdmissionService.java) 先从 [AgentMemoryStore](../../apps/server/src/main/java/com/chtholly/agent/memory/AgentMemoryStore.java) 捕获 generation，再由 [AgentTurnCoordinator](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentTurnCoordinator.java) 用 Redis Lua提供跨实例单飞与 request 去重；成功注册 active turn 后，[AgentWebSocketAcceptedTurnRunner](../../apps/server/src/main/java/com/chtholly/agent/ws/AgentWebSocketAcceptedTurnRunner.java) 发送 `accepted` 并调用只有门面职责的 [ChthollyAgent](../../apps/server/src/main/java/com/chtholly/agent/ChthollyAgent.java)。[AgentTurnOrchestrator](../../apps/server/src/main/java/com/chtholly/agent/runtime/AgentTurnOrchestrator.java) 依次完成准备、边界/loop、最终回答、Memory 与 Trace 阶段；[AgentLoopExecutor](../../apps/server/src/main/java/com/chtholly/agent/runtime/AgentLoopExecutor.java) 只维护状态迁移，LLM 重试、Action 解析、工具 Trace、Evidence 和复合任务完成门槛分别由独立协作者处理。服务端会删除模型伪造的 `_userQuestion` / `_conversationHistory` 等内部工具字段。`web_search` 只发现候选；只有 `web_fetch` 请求命中累计候选且产出绑定同 URL 的 PUBLIC WEB Evidence 才解除待核验状态。最终生成、引用修复和 Skill 校验共享最终 Evidence 快照，通过后一次发送完整 delta 与 final。
- **异步/缓存**：消息在 Agent executor 执行；正在执行的本连接 turn 同时保留可取消任务与事件围栏。连接关闭或任一 WebSocket 写入失败会取消 turn、中断本地任务并拒绝迟到事件，但关闭回调不释放 active lease；worker 完成取消/退出、形成客户端交付决议后，才在自身 `finally` 释放租约并移除 active turn，因此同一逻辑会话不会在旧 worker 尚未退出时启动下一轮。单轮 Memory 由一个 Redis Lua 在 memory generation、active lease 与 Redis 时间 deadline 围栏内完成成对追加、裁剪和 memory/generation 双 TTL 刷新；非 `COMMITTED` 不发送答案。会话清空原子换入新的有限期 UUID generation 并删除正文，但保留 active lease 到旧 turn 正常释放；旧快照的 fenced/unfenced 写入都会以 `SESSION_CLEARED` 拒绝。终态决议再回调完成 Trace 的 Span、日志、指标与异步持久化。角色状态更新、会话反思与认知周期在扩展任务中运行，不阻塞客户端。
- **状态**：每个 turn 由 `requestId + turnId` 关联协议事件、日志与 Trace；Trace 的 `turn`、`toolPlan`、`answerTiming`、`memory` 分别记录身份/预算/中止位置/客户端交付、有效工具、答案可见节点与会话写入结果。`agent-trace-v4` 还按事件保存管理员诊断所需的问题/页面上下文、每次 LLM 输入输出、工具实际输入/最终 Observe/外部条件、最终答案与失败因果链，顶层 Step 投影保留每步 action 与 LLM/工具耗时，完整度投影独立报告事件丢弃和工具预览截断；内容有整轮容量边界并只遮蔽基础设施凭证。会话记忆在 Redis 与进程缓存；动态 Evidence 只在本轮不可变快照中累积；Trace/经验/图谱按已启用扩展写 MySQL；模型状态在外部 LLM。Trace 用稳定 `outcomeReason` 区分 `NEEDS_CLARIFICATION`、`NO_EVIDENCE`、`INVALID_CITATION` 和 `MODEL_FAILURE`，自然语言文案不承担机器状态职责。
- **失败/降级**：取得 turn 所有权前的输入、限流、并发或去重问题使用仅携带 `requestId` 的 `rejected`；成功 `accepted` 后的 `think/act/observe/delta/final/error` 必须同时匹配 `requestId + turnId`。输入预检未通过时先用角色魂生成澄清回复，不检索也不进入 loop；`REQUIRED` 证据为空或引用校验失败时，候选答案不会进入 delta、memory 或成功 trace。公网 URL、DNS、redirect、robots、媒体类型、体积、provider 与限流异常使用稳定工具错误码进入 Observe，失败调用不会产生 Evidence；Agent 可以在剩余步数和整轮预算内换来源或诚实说明边界。复合 Bangumi 请求只在必需工具尚未调用或参数校验失败时保持 `PENDING`；成功转为 `SATISFIED`，provider `ERROR`、`TIMEOUT` 或 `INTERRUPTED` 转为 `BLOCKED`。`BLOCKED` 不会继续拒绝 final 直至耗尽最大步数：本轮已有 Evidence 时只能在其范围内给出部分答案，没有可回答 Evidence 时只说明 provider 不可用，不能把失败 Observation 当成事实证据；`VALIDATION_ERROR` 仍要求在剩余预算内修正参数重试。Memory 的 stale/deadline 拒绝及提交状态未知都会失败关闭，并记录 `MEMORY_WRITE_FAILED` 与具体状态；会话生命周期删除失败时前端保留本地消息和会话并展示可重试错误，不把本地删除伪装成后端成功。Redis 提交和浏览器收到终态之间仍不是端到端 exactly-once，若未来要求消除这一边界需引入客户端 ACK 两阶段协议。整轮耗尽返回 `TURN_TIMEOUT` 并在 Trace 记录阶段；断线取消标记为 `ABORTED/CANCELLED`，不声称可续传旧输出。终态写入失败会关闭连接并记录 `CLIENT_DELIVERY_FAILED`。终态已送达后发生 lease 释放失败时，服务端不会伪造一个新的错误或覆盖客户端已经看到的 final；Trace 保留真实 `DELIVERED`，另记 `turn_coordination_release` 失败并关闭连接，Redis 中的旧 lease 由安全 TTL 最终释放。`llm.enabled=false` 时 WebSocket/Agent Bean 不装配，主站仍运行；Redis 协调失败时拒绝新 turn，不退回无单飞保护的执行。
- **代表性测试**：[AgentWebSocketHandlerTest](../../apps/server/src/test/java/com/chtholly/agent/ws/AgentWebSocketHandlerTest.java)、[AgentWebSocketConnectionLifecycleTest](../../apps/server/src/test/java/com/chtholly/agent/ws/AgentWebSocketConnectionLifecycleTest.java)、[AgentWebSocketActiveTurnTest](../../apps/server/src/test/java/com/chtholly/agent/ws/AgentWebSocketActiveTurnTest.java)、[AgentSessionMemoryControllerSecurityTest](../../apps/server/src/test/java/com/chtholly/agent/api/AgentSessionMemoryControllerSecurityTest.java)、[AgentTurnCoordinatorTest](../../apps/server/src/test/java/com/chtholly/agent/ws/AgentTurnCoordinatorTest.java)、[AgentLoopExecutorTest](../../apps/server/src/test/java/com/chtholly/agent/runtime/AgentLoopExecutorTest.java)、[AgentLoopCompletionPolicyTest](../../apps/server/src/test/java/com/chtholly/agent/runtime/AgentLoopCompletionPolicyTest.java)、[BangumiToolFailureContractTest](../../apps/server/src/test/java/com/chtholly/agent/tools/BangumiToolFailureContractTest.java)、[AgentLoopExecutorArchitectureTest](../../apps/server/src/test/java/com/chtholly/agent/runtime/AgentLoopExecutorArchitectureTest.java)、[AgentTurnBudgetTest](../../apps/server/src/test/java/com/chtholly/agent/runtime/AgentTurnBudgetTest.java)、[ChthollyAgentTest](../../apps/server/src/test/java/com/chtholly/agent/ChthollyAgentTest.java)、[AgentMemoryStoreRedisIT](../../apps/server/src/test/java/com/chtholly/agent/memory/AgentMemoryStoreRedisIT.java)。

## 9. Seed 生成与发布

- **触发入口**：启动参数或 [run-seed.ps1](../../scripts/dev/run-seed.ps1) 触发 [SeedRunner](../../apps/server/src/main/java/com/chtholly/seed/SeedRunner.java)，再调用 [SeedOrchestrator](../../apps/server/src/main/java/com/chtholly/seed/SeedOrchestrator.java)。
- **同步主链**：解析 mode/dry-run，检查 MySQL marker，构建 Bangumi 推荐、账号、文章、评论和关注计划；非 dry-run 在事务内持久化，正文发布器存在时上传 Markdown；搜索索引服务存在时逐篇 upsert ES，最后写 marker。
- **异步/缓存**：可选 [SeedInteractionService](../../apps/server/src/main/java/com/chtholly/seed/SeedInteractionService.java) 调度多轮互动并用 Redis 保存状态；dry-run 只生成摘要，不写状态。
- **状态**：marker 与业务 seed 行在 MySQL；正文位于当前 StorageService；互动运行态在 Redis；ES 是派生索引。
- **失败/降级**：已存在 marker 时幂等跳过；正文发布 IOException、序列化或 ES 索引失败会终止运行并回滚 MySQL 事务，但已经写出的外部对象不受数据库事务回滚。可选正文发布器、搜索索引服务或互动服务不存在时，对应步骤跳过。
- **代表性测试**：[SeedRunModeTest](../../apps/server/src/test/java/com/chtholly/seed/SeedRunModeTest.java)、[SeedOrchestratorTest](../../apps/server/src/test/java/com/chtholly/seed/SeedOrchestratorTest.java)、[SeedInteractionServiceTest](../../apps/server/src/test/java/com/chtholly/seed/SeedInteractionServiceTest.java)。

## 10. 管理员治理与审计

- **触发入口**：[AdminUserController](../../apps/server/src/main/java/com/chtholly/admin/api/AdminUserController.java) 与 [AdminPostController](../../apps/server/src/main/java/com/chtholly/admin/api/AdminPostController.java)，类级 [RequireRole](../../apps/server/src/main/java/com/chtholly/admin/role/RequireRole.java) 要求 ADMIN。
- **同步主链**：[RequireRoleAspect](../../apps/server/src/main/java/com/chtholly/admin/role/RequireRoleAspect.java) 校验角色；[AdminUserService](../../apps/server/src/main/java/com/chtholly/admin/service/AdminUserService.java) 修改角色/封禁，[AdminPostService](../../apps/server/src/main/java/com/chtholly/admin/service/AdminPostService.java) 修改可见性或软删文章/评论；随后调用 [AdminAuditService](../../apps/server/src/main/java/com/chtholly/admin/service/AdminAuditService.java) 尝试写审计。
- **异步/缓存**：封禁同步撤销目标用户全部 refresh token；内容治理复用文章缓存失效、Outbox 与 ES 尽力同步路径，没有单独审计队列。
- **状态**：角色、封禁时间、内容状态、审计日志与 `refresh_session_epoch` 在 MySQL；refresh JTI membership 在 Redis。
- **失败/降级**：非管理员拒绝；不能封禁自己/站长或移除站长角色。当前 `AdminAuditService` 捕获序列化/插入异常并记录警告，因此审计是 best-effort，失败不会回滚已经完成的治理变更；内容治理的 ES/cache 派生状态仍遵循文章链路边界。
- **代表性测试**：[RequireRoleAspectTest](../../apps/server/src/test/java/com/chtholly/admin/role/RequireRoleAspectTest.java)、[RefreshSessionEpochRedisStoreIT](../../apps/server/src/test/java/com/chtholly/integration/RefreshSessionEpochRedisStoreIT.java) 覆盖管理员封禁与 epoch 同事务回滚；控制器和审计异常的直接覆盖仍按各自局部测试维护。

## 修改联动

修改一条链路时，至少同时检查入口契约、同步事务、事件生产者/消费者、缓存失效、状态权威性、降级响应与上述代表性测试；不要只更新调用链的一端。
