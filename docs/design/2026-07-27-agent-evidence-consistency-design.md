# Agent 证据、工具与文章陪读一致性修复设计

## 1. 背景

当前文章问答、完整 Agent、Bangumi 工具与搜索聚合分别具备可用能力，但它们之间的上下文、证据和错误契约不一致，产生了以下用户可见问题：

- “只依据当前文章”只读取页面摘要，没有读取当前文章正文；
- 普通 Bangumi 工具查询被站内证据引用门禁误伤，工具已有结果仍被替换为“当前证据不足”；
- 证据型任务已有证据但回答遗漏 `[E#]` 时直接拒绝，没有有限修复机会；
- Bangumi 本地搜索按评分优先，衍生节目可能压过标题完全匹配的主体；
- 复合问题只调用一个工具，出现作品资料完整但角色部分缺失；
- 临时模型调用异常统一显示为“检查 LLM 配置”，无法区分配置、限流、超时和上游错误；
- 搜索聚合卡片保留 Elasticsearch 中的旧点赞、收藏计数；
- 文章内问答使用日文字体栈并按纯文本展示；
- 从文章进入“珂朵莉陪读”时复用普通会话历史，没有明确显示当前文章上下文。

本次修复不修改端口、模型参数、密钥、外部服务地址或运行环境配置。

## 2. 目标与非目标

### 2.1 目标

1. 证据型任务保持可验证、失败关闭，同时减少错误拒绝。
2. 当前文章请求始终以当前文章正文为唯一文章证据域。
3. 普通站内与 Bangumi 工具问答可以使用工具观察结果自然回答，不被无关站内引用门禁拦截。
4. Bangumi 精确标题和复合问题得到稳定、完整的工具结果。
5. 模型临时异常可重试、可观测，错误提示符合真实故障类型。
6. 修复搜索计数、文章问答排版和文章陪读会话的已知一致性问题。

### 2.2 非目标

- 不取消证据任务的引用校验；
- 不将完整 Agent 与文章内轻量问答合并为同一套前端组件；
- 不重写 ReAct 运行时或引入新的工作流引擎；
- 不调整现有模型温度、上下文窗口、超时和端口配置；
- 不迁移或重建已有用户会话数据。

## 3. 方案选择

采用“修正契约并增加一次有限修复”的方案。

不采用简单关闭引用门禁：这会让证据大纲、事实核查等任务失去可验证性。也不在本次整体重写 Agent 编排：范围过大，且会把内容检索、工具调用和前端会话三个独立问题耦合到一起。

## 4. 设计

### 4.1 分离检索请求与强制引用

`ContextContribution` 与 `ContextSnapshot` 中保留两个不同语义：

- `retrievalRequested`：本轮需要补充检索上下文；
- `evidenceRequired`：最终答案必须引用 Evidence。

普通查询词触发知识检索时只设置 `retrievalRequested`。只有下列情况设置 `evidenceRequired`：

- 显式选择了要求证据的 Skill；
- 用户明确要求“只依据”“证据”“标出 Evidence”等可验证输出；
- 调用方通过任务契约明确要求证据。

Bangumi 等结构化工具的 Observation 不再因为站内混合检索而被迫引用无关 `[E#]`。

### 4.2 当前文章的证据域

扩充 Skill 选择规则，识别：

- 当前文章、这篇文章、只依据本文；
- 总结、概括、主要观点；
- 证据、依据、Evidence。

页面上下文中的文章 slug 或 ID 由后端解析为已发布文章。新增可复用的“按文章检索正文分块”能力，底层继续使用现有 RAG 索引和分块结果，但查询必须附带文章 ID 过滤。

当前文章任务生成的 Evidence 只允许来自该文章。没有当前文章上下文、文章不可访问或正文索引不可用时保持失败关闭，不退化为全站语义搜索。

### 4.3 引用修复

当且仅当满足以下条件时进行一次引用修复：

- 本轮确实要求证据；
- EvidenceSet 非空；
- 初次答案内容非空；
- 校验结果仅为 `MISSING_CITATION`，不存在未知编号或证据越界。

修复请求只允许模型在原答案中补充或调整 `[E#]`，不得引入新事实。修复后重新执行同一校验；仍失败则使用现有证据不足响应。该流程最多一次，避免循环和额外不可控延迟。

### 4.4 Bangumi 检索与复合问题

本地 SQL 排序改为：

1. 中文名或原名完全匹配；
2. 中文名或原名前缀匹配；
3. 其他包含匹配；
4. 同相关度内再按评分、排名排序。

工具描述和运行时提示明确：一个问题同时要求作品资料和角色时，搜索成功后必须继续调用角色工具。工具执行器仍保持单一职责，不把角色查询硬编码进搜索工具。

### 4.5 模型错误处理与观测

模型调用失败按以下类别记录：

- 缺少配置或模型客户端不可用；
- 超时；
- 限流；
- 临时上游或网络错误；
- 不可重试的请求错误。

只对明确可重试的异常进行一次重试，复用现有超时与模型参数，不新增配置项。执行追踪记录失败调用、异常类别和重试次数。

用户提示区分：

- 配置缺失：提示检查 LLM 配置；
- 临时失败：提示模型服务暂时不可用，可稍后重试；
- 证据不足：保持证据不足提示。

### 4.6 搜索计数一致性

搜索聚合命中仍从 Elasticsearch 获取文章主体和排序信息，但返回前批量从权威计数服务补齐：

- 点赞总数；
- 收藏总数；
- 评论总数。

采用批量读取避免逐条查询。ES 中的计数字段只作为降级回退，不作为正常返回的权威值。

### 4.7 文章内问答展示

- 回答区域改用站点中文正文变量，不再强制日文字体；
- 使用现有安全 Markdown 展示组件或同等渲染策略，支持段落、列表、强调和行内代码；
- 保持流式文本在未完成时也能稳定渲染；
- 不允许原始 HTML。

### 4.8 文章陪读会话

从文章侧边栏进入 Agent 时：

- 以 `post:<slug>` 作为文章上下文键；
- 创建或复用该文章对应的专属本地会话；
- 不自动混入当前普通会话的旧历史；
- 工作区显示“正在陪读《文章标题》”上下文提示；
- 每条消息继续携带文章上下文，后端据此限定当前文章证据域。

用户主动切换到其他普通会话时，文章上下文不泄漏到该会话。

## 5. 数据流

```text
文章页
  ├─ 轻量问答 → postId 限定的 RAG → 流式回答 → Markdown 展示
  └─ 珂朵莉陪读 → 文章专属会话 → WebSocket 请求携带 post:<slug>
                                      ↓
                                Skill 选择与意图判断
                                      ↓
                       当前文章 Evidence / 站内检索 / Bangumi 工具
                                      ↓
                         仅证据任务执行引用校验与一次修复
                                      ↓
                              流式回答与执行追踪
```

## 6. 测试与验收

### 6.1 后端回归

- 当前文章总结请求选择文章证据技能；
- 当前文章 Evidence 全部属于目标文章；
- 普通 Bangumi 工具结果不因缺少站内引用而被拒绝；
- 证据回答缺少引用时只修复一次；
- 修复后仍无效时保持失败关闭；
- 精确《迷宫饭》排在衍生广播节目之前；
- 复合作品资料与角色问题会完成两个工具阶段；
- 可重试模型错误重试一次，并记录失败类型；
- 搜索聚合返回权威点赞、收藏和评论计数。

### 6.2 前端回归

- 文章问答使用中文正文字体；
- Markdown 段落、列表、强调正确显示；
- 从不同文章进入陪读会创建或复用各自文章会话；
- 文章会话不显示普通会话历史；
- 页面显示当前陪读文章提示。

### 6.3 用户场景验收

使用以下原始问题进行端到端验证：

1. `只依据当前文章，总结作者的三个主要观点，并标出证据编号`
2. `站内有哪些文章讨论了《迷宫饭》？列出标题和每篇关注的重点`
3. `查询《迷宫饭》的评分、集数和放送时间。《迷宫饭》的主要角色有哪些？`
4. `基于站内文章，为“京都动画如何表现人物关系”生成一个至少四节的证据大纲，每节标出 Evidence。`

同时验证文章详情与搜索首页的点赞、收藏、评论计数一致，以及文章问答和陪读入口的展示行为。

## 7. 风险与回退

- 引用修复会增加一次模型调用：仅在证据充足且唯一问题是缺少引用时触发。
- 当前文章严格限定可能暴露旧索引缺失：索引不可用时明确失败，不静默混入其他文章。
- 搜索计数实时补齐增加一次批量缓存/数据库读取：保留 ES 值作为降级回退。
- 文章会话按上下文键复用可能遇到旧本地数据：读取时兼容无上下文字段的历史会话，将其视为普通会话。

所有改动按职责拆分提交，任一子模块都可独立回退，不涉及数据库破坏性迁移。
