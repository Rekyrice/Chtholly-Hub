# 用户主页评论活动设计

## 背景

用户主页目前能够展示公开文章，但“最近的回应”和“评论”标签仍是占位内容。评论后端只支持按文章查询评论树，无法直接回答“某个用户最近在站内留下了哪些公开回应”。如果由前端遍历文章并逐篇查询，不仅会产生 N+1 请求，也无法覆盖用户在其他作者文章下留下的评论。

本设计新增一个面向用户主页的公开评论活动查询，并由概览与评论标签共同复用。

## 目标

- 概览区展示该用户最近 2 条公开评论或回复。
- “评论”标签分页展示该用户的全部公开评论活动。
- 每条活动能够说明用户评论或回复了哪篇文章，并可跳转文章详情。
- 公开主页不得泄露非公开文章、未发布文章或已删除评论。
- 保持现有评论创建、文章评论树和删除行为不变。

## 非目标

- 不展示用户收到的回复或通知；这里展示的是该用户主动留下的评论。
- 不展示点赞、收藏或其他互动活动。
- 不修改评论嵌套层级，也不新增评论编辑能力。
- 不为主页访问者开放私密、粉丝可见、同校可见或不列出的文章评论。

## 方案选择

采用独立的用户评论活动接口：

```http
GET /api/v1/users/{userId}/comments?page=1&size=20
```

该接口的资源语义是“某个用户的公开评论活动”，不会把用户筛选参数混入现有的文章评论树接口。后端能够在一次分页查询中联结评论与文章元数据，避免前端 N+1 请求。

## 后端设计

### 接口与返回结构

接口公开可读，`page` 从 1 开始，`size` 范围为 1 至 50，返回现有 `PageResponse` 结构。单条活动包含：

| 字段 | 含义 |
|------|------|
| `id` | 评论 ID，使用字符串传输 Snowflake ID |
| `postId` | 文章 ID |
| `postSlug` | 文章详情路由 slug |
| `postTitle` | 文章标题 |
| `parentId` | 父评论 ID；为空表示顶级评论 |
| `content` | 已清洗的评论正文 |
| `createdAt` | 评论创建时间 |

评论作者信息不重复返回，因为用户主页已经拥有确定的用户上下文。

### 查询规则

Mapper 使用评论表联结文章表，查询与计数必须使用完全相同的可见性条件：

- `comments.user_id = userId`
- `comments.deleted_at IS NULL`
- `posts.status = 'published'`
- `posts.visible = 'public'`

结果按 `comments.created_at DESC, comments.id DESC` 排序，以 ID 作为同一毫秒内的稳定次序。顶级评论和回复都作为独立活动返回，不展开回复树。

新增 `V30__comment_user_activity_index.sql`，为评论表补充 `(user_id, deleted_at, created_at, id)` 复合索引，并同步 `schema.sql`。该索引同时服务用户过滤、软删除过滤与倒序分页，避免评论量增长后退化为按用户全表扫描和额外排序。

### 服务边界

- 在评论模块新增 `UserCommentController` 承载 `/api/v1/users/{userId}/comments`，避免受现有 `CommentController` 的文章级类路由限制，也避免让用户模块反向依赖评论模块。
- `CommentService` 提供只读的 `listByUser` 用例。
- `CommentMapper` 负责列表与总数查询。
- 新增专用响应 DTO 和查询行模型，不复用文章评论树 DTO，避免把 `replies` 等无关字段带入主页接口。
- `SecurityConfig` 显式放行 `GET /api/v1/users/*/comments`；现有 `/api/v1/users/*` 只覆盖单段用户资料路由，不能依赖它隐式放行两段子资源。

查询不到评论时返回空分页，不将“无评论”视为错误。用户 ID 不存在时也返回空分页，避免为了公开活动查询额外引入用户存在性查询；个人主页本身已经负责确认用户存在。

## 前端设计

### 数据流

1. 用户主页 Server Component 在取得用户后，请求第一页评论活动，默认 `size=20`。
2. 初始分页结果作为属性传入 `UserTabs`，与公开文章初始数据一起完成首屏渲染。
3. 概览从活动列表取前 2 条。
4. “评论”标签展示当前已加载的活动；存在下一页时，客户端通过 `commentService` 请求下一页并追加。
5. 分页请求期间禁用“加载更多”，防止重复提交；失败后保留已加载内容并允许重试。

### 展示规则

每条活动显示：

- `parentId` 非空时使用“回复了《文章标题》”，否则使用“评论了《文章标题》”；不在接口中维护重复的布尔状态。
- 评论正文完整展示，由样式控制换行；不在数据层截断。
- 展示相对或格式化时间。
- 标题及活动卡片链接到 `/post/{postSlug}`。

概览无数据时显示安静的空状态，不再出现“接口还没接上”的开发占位文案。“评论”标签无数据时使用同一语义的空状态。

### 失败处理

- 首次服务端请求失败时，主页主体仍可渲染；评论区域显示“回应暂时没有加载出来”，并提供客户端重试。
- 加载更多失败时不清空已有评论，只在列表下方显示错误和重试入口。
- 接口返回重复 ID 时，前端追加数据按评论 ID 去重，避免重试造成重复卡片。

## 安全与一致性

- 公开接口不根据当前登录用户放宽文章可见性，确保同一主页对所有访问者返回一致结果。
- 软删除评论不返回，避免泄露删除前正文。
- 回复不会携带父评论正文，避免通过活动接口间接暴露已删除或不可见上下文。
- 所有 Snowflake ID 继续以字符串输出，避免 JavaScript 精度损失。

## 测试策略

### 后端

- Mapper 契约测试覆盖联表字段、公开性过滤、软删除过滤、稳定排序与分页参数。
- 数据库测试覆盖用户评论活动复合索引已出现在迁移和完整 schema 中。
- Service 测试覆盖空结果、分页元数据、顶级评论与回复映射、Snowflake ID 字符串化。
- Controller 测试覆盖默认分页、非法分页参数和公开访问；安全配置测试确认匿名请求可以访问用户评论活动接口，而写请求仍不被额外放行。

### 前端

- `commentService` 测试覆盖请求路径与分页参数。
- `UserTabs` 测试覆盖概览最近 2 条、评论标签完整首屏、回复文案、空态、首次失败、加载更多、失败重试和 ID 去重。
- 页面测试覆盖服务端初始数据传递与降级标记。

### 回归

- 后端运行评论领域定向测试后执行全量 `mvn test`。
- 前端运行目标 Vitest 后执行 `npm run test:run` 和 `npm run build`。

## 验收标准

- 有评论的用户主页概览准确显示最新 2 条公开回应。
- “评论”标签能分页浏览该用户的公开评论与回复，顺序稳定且无重复。
- 点击活动能够进入对应文章。
- 私密或未发布文章下的评论、软删除评论不会出现在接口或页面中。
- 空数据与请求失败都有面向用户的状态，不再展示开发占位文案。
